# 第 6 课：事务 - 保证数据不会乱

## 一个灾难性的 Bug

你的转账功能上线了，代码如下：

```javascript
// ❌ 危险的代码
async function transfer(fromUser, toUser, amount) {
  // 1. 扣款
  await db.execute(
    'UPDATE accounts SET balance = balance - ? WHERE user_id = ?',
    [amount, fromUser]
  );
  
  // 💥 如果这里程序崩溃了...
  
  // 2. 加款
  await db.execute(
    'UPDATE accounts SET balance = balance + ? WHERE user_id = ?',
    [amount, toUser]
  );
}
```

**灾难场景**：
- Alice 给 Bob 转 100 元
- 第 1 步执行成功：Alice 账户 -100
- 服务器突然断电 💥
- 第 2 步没执行：Bob 没收到钱

**结果**：100 元人间蒸发了！

## 事务来救场

```javascript
// ✅ 正确的代码
async function transfer(fromUser, toUser, amount) {
  const conn = await db.getConnection();
  
  try {
    // 开启事务
    await conn.beginTransaction();
    
    // 1. 扣款
    await conn.execute(
      'UPDATE accounts SET balance = balance - ? WHERE user_id = ?',
      [amount, fromUser]
    );
    
    // 2. 加款
    await conn.execute(
      'UPDATE accounts SET balance = balance + ? WHERE user_id = ?',
      [amount, toUser]
    );
    
    // 提交：两步都成功，一起生效
    await conn.commit();
  } catch (error) {
    // 回滚：任何一步失败，全部撤销
    await conn.rollback();
    throw error;
  } finally {
    conn.release();
  }
}
```

**SQL 版本**：

```sql
START TRANSACTION;

UPDATE accounts SET balance = balance - 100 WHERE user_id = 'Alice';
UPDATE accounts SET balance = balance + 100 WHERE user_id = 'Bob';

COMMIT;  -- 成功提交
-- 或
-- ROLLBACK;  -- 出错回滚
```

## 什么是事务？

**事务（Transaction）** = 一组 SQL 操作的集合，要么全部成功，要么全部失败。

**前端类比**：

```javascript
// 就像 Promise.all()
Promise.all([
  deductMoney(alice, 100),
  addMoney(bob, 100)
])
.then(() => console.log('转账成功'))
.catch(() => console.log('转账失败，全部撤销'));
```

## ACID 特性（面试必考）

### A - Atomicity（原子性）

**要么全做，要么全不做**，不存在"做一半"。

```sql
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE user_id = 1;
-- 💥 这里崩溃了
UPDATE accounts SET balance = balance + 100 WHERE user_id = 2;
COMMIT;
```

因为没有 COMMIT，MySQL 会自动 ROLLBACK，第一条 UPDATE 也会撤销。

### C - Consistency（一致性）

**数据始终处于合法状态**。

例如：转账前后，总金额不变。

```sql
-- 转账前
Alice: 1000
Bob:   500
总计:  1500

-- 转账 100 后
Alice: 900
Bob:   600
总计:  1500  ✅ 一致性保持
```

### I - Isolation（隔离性）

**并发事务互不干扰**。

假设两个用户同时给 Bob 转账：

```sql
-- 事务 1: Alice → Bob (100)
-- 事务 2: Charlie → Bob (50)
```

如果没有隔离性，Bob 可能只收到 50 或 100，而不是 150。

### D - Durability（持久性）

**提交后，数据永久保存**，即使断电也不会丢失。

MySQL 通过 **redo log** 实现：事务提交时，先写日志，再慢慢写磁盘。

## 并发问题：三个经典 Bug

### 问题 1：脏读（Dirty Read）

```sql
-- 时间线 | 事务 A                          | 事务 B
-- -------|--------------------------------|---------------------------
-- T1     | START TRANSACTION;             |
-- T2     | UPDATE accounts SET balance=0  |
--        | WHERE user_id = 'Alice';       |
-- T3     |                                | SELECT balance FROM accounts
--        |                                | WHERE user_id = 'Alice';
--        |                                | -- 读到 0（脏数据）
-- T4     | ROLLBACK;                      |
--        | -- Alice 的余额恢复原值         |
-- T5     |                                | -- B 以为 Alice 没钱了 😱
```

**问题**：B 读到了 A 未提交的数据，而 A 后来回滚了。

### 问题 2：不可重复读（Non-repeatable Read）

```sql
-- 事务 B 在一个事务内查询两次，结果不一样

-- T1: B 读取 Alice 余额
SELECT balance FROM accounts WHERE user_id = 'Alice';  -- 1000

-- T2: A 修改并提交
UPDATE accounts SET balance = 500 WHERE user_id = 'Alice';
COMMIT;

-- T3: B 再次读取
SELECT balance FROM accounts WHERE user_id = 'Alice';  -- 500

-- B: "我没动啊，怎么变了？" 😱
```

### 问题 3：幻读（Phantom Read）

```sql
-- T1: B 统计年龄 > 18 的用户
SELECT COUNT(*) FROM users WHERE age > 18;  -- 返回 10

-- T2: A 插入一个新用户（age=20）
INSERT INTO users (name, age) VALUES ('Tom', 20);
COMMIT;

-- T3: B 再次统计
SELECT COUNT(*) FROM users WHERE age > 18;  -- 返回 11

-- B: "刚才明明是 10 个，怎么多了一个？" 😱
```

## 隔离级别：如何解决并发问题

MySQL 提供 4 种隔离级别：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 性能 |
|---------|------|-----------|------|------|
| **READ UNCOMMITTED** | ✅ 会发生 | ✅ 会发生 | ✅ 会发生 | 最快 |
| **READ COMMITTED** | ❌ 已解决 | ✅ 会发生 | ✅ 会发生 | 较快 |
| **REPEATABLE READ** | ❌ 已解决 | ❌ 已解决 | ⚠️ 大部分解决 | 较慢 |
| **SERIALIZABLE** | ❌ 已解决 | ❌ 已解决 | ❌ 已解决 | 最慢 |

**MySQL 默认级别**：`REPEATABLE READ`（可重复读）

**查看当前隔离级别**：

```sql
SELECT @@transaction_isolation;
-- 输出: REPEATABLE-READ
```

**设置隔离级别**：

```sql
-- 设置当前会话
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 设置全局
SET GLOBAL TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

### 各级别的适用场景

**READ UNCOMMITTED**：
- 几乎不用，数据可能是错的

**READ COMMITTED**：
- Oracle、PostgreSQL 的默认级别
- 适合对一致性要求不高的场景

**REPEATABLE READ**：
- MySQL 的默认级别
- 适合大部分业务场景
- 电商、金融等推荐使用

**SERIALIZABLE**：
- 完全串行化，性能差
- 只在对数据一致性要求极高的场景使用

## 锁机制

### 乐观锁 vs 悲观锁

#### 悲观锁：直接锁住数据

**场景**：秒杀商品，库存只有 1 件

```sql
START TRANSACTION;

-- FOR UPDATE: 锁住这行数据
SELECT stock FROM products WHERE id = 1 FOR UPDATE;

-- 检查库存
-- 如果 stock > 0，扣减库存
UPDATE products SET stock = stock - 1 WHERE id = 1;

COMMIT;
```

**特点**：
- ✅ 安全可靠
- ❌ 性能较差（其他请求要排队）

#### 乐观锁：通过版本号控制

**场景**：抢票，读多写少

```sql
-- 商品表增加 version 字段
CREATE TABLE products (
  id INT PRIMARY KEY,
  name VARCHAR(100),
  stock INT,
  version INT DEFAULT 0
);
```

**JavaScript 代码**：

```javascript
async function buyProduct(productId) {
  // 1. 查询商品（不加锁）
  const [rows] = await db.execute(
    'SELECT stock, version FROM products WHERE id = ?',
    [productId]
  );
  
  const { stock, version } = rows[0];
  
  if (stock <= 0) {
    throw new Error('库存不足');
  }
  
  // 2. 更新时带上版本号
  const [result] = await db.execute(
    'UPDATE products SET stock = stock - 1, version = version + 1 WHERE id = ? AND version = ?',
    [productId, version]
  );
  
  // 3. 检查更新结果
  if (result.affectedRows === 0) {
    throw new Error('购买失败，请重试');  // 被别人抢先了
  }
  
  return '购买成功';
}
```

**特点**：
- ✅ 性能好（无锁）
- ⚠️ 可能需要重试
- ✅ 适合读多写少的场景

### 死锁

**场景**：

```sql
-- 事务 A
START TRANSACTION;
UPDATE orders SET status = 'paid' WHERE id = 1;  -- 锁住订单 1
-- 等待锁定用户 1...
UPDATE users SET balance = balance - 100 WHERE id = 1;

-- 事务 B
START TRANSACTION;
UPDATE users SET balance = balance + 50 WHERE id = 1;  -- 锁住用户 1
-- 等待锁定订单 1...
UPDATE orders SET status = 'shipped' WHERE id = 1;
```

**结果**：A 等 B 释放用户 1，B 等 A 释放订单 1，形成死锁。

**MySQL 的处理**：
- 自动检测死锁
- 回滚其中一个事务（通常是修改较少的）

**避免死锁的方法**：
1. 保持事务简短
2. 访问多个表时，保持一致的顺序
3. 使用合理的索引

## 常见问题

### Q1: 什么时候需要事务？

**需要事务的场景**：
- ✅ 转账、支付
- ✅ 订单创建（涉及多个表）
- ✅ 库存扣减
- ✅ 任何"要么全成功、要么全失败"的操作

**不需要事务的场景**：
- ❌ 单条 SELECT 查询
- ❌ 单条 INSERT（已经是原子的）
- ❌ 日志记录

### Q2: 事务越长越好吗？

❌ 不！事务应该尽可能短。

```javascript
// ❌ 糟糕的做法
await conn.beginTransaction();
await sendEmail();  // 发邮件很慢，不要放在事务里！
await updateDatabase();
await conn.commit();

// ✅ 正确的做法
await conn.beginTransaction();
await updateDatabase();
await conn.commit();
await sendEmail();  // 数据库操作完成后再发邮件
```

### Q3: 隔离级别怎么选？

**推荐**：
- 大部分场景：使用 MySQL 默认的 `REPEATABLE READ`
- 对性能要求高：`READ COMMITTED`
- 对一致性要求极高：`SERIALIZABLE`

## 总结

**事务的本质**：
- 保证一组操作的原子性
- 通过 ACID 特性保证数据安全

**关键点**：
- ✅ 转账、支付等关键操作必须用事务
- ✅ 事务要尽可能短
- ✅ 使用乐观锁处理高并发读写
- ✅ 避免死锁：保持访问顺序一致

**前端角度理解**：
```javascript
// 事务 = Promise.all()
// 乐观锁 = 版本号 + 重试
// 悲观锁 = 互斥锁
```
