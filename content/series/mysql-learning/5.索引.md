# 第 5 课：索引 - 让查询快 1000 倍

## 一个性能问题

假设你的 `users` 表有 100 万条数据，现在要查询：

```sql
SELECT * FROM users WHERE email = 'alice@example.com';
```

**没有索引**：MySQL 要扫描 100 万行，逐行对比 email。
- 耗时：**2.5 秒**

**有索引**：MySQL 通过索引直接定位。
- 耗时：**0.001 秒**（快了 2500 倍！）

## 什么是索引？

> 索引就像书的**目录**。

**没有目录（全表扫描）**：
- 要找"第 8 章：索引"这个词？
- 从第 1 页翻到最后一页 ❌

**有目录（走索引）**：
- 查目录，直接翻到第 156 页 ✅

### 前端类比

```javascript
// 没有索引 = 遍历数组
const user = users.find(u => u.email === 'alice@example.com');
// 时间复杂度：O(n)

// 有索引 = 用 Map 查找
const userMap = new Map(users.map(u => [u.email, u]));
const user = userMap.get('alice@example.com');
// 时间复杂度：O(1)
```

## 创建索引

### 主键索引（已经有了）

```sql
CREATE TABLE users (
  id INT PRIMARY KEY,  -- 这就是主键索引
  ...
);
```

主键自动创建索引，无需额外操作。

### 普通索引

```sql
-- 给 email 字段加索引
CREATE INDEX idx_email ON users(email);
```

现在查询 email 就快了：

```sql
SELECT * FROM users WHERE email = 'alice@example.com';
-- 速度：从秒级 → 毫秒级
```

### 唯一索引

```sql
-- 既加速查询，又保证唯一性
CREATE UNIQUE INDEX idx_username ON users(username);
```

### 联合索引（重要！）

```sql
-- 组合多个字段
CREATE INDEX idx_name_age ON users(name, age);
```

## 最重要的规则：最左前缀原则

对于联合索引 `(a, b, c)`：

```sql
CREATE INDEX idx_abc ON users(name, age, city);
```

**能用到索引的查询**：

```sql
✅ WHERE name = 'Alice'
✅ WHERE name = 'Alice' AND age = 25
✅ WHERE name = 'Alice' AND age = 25 AND city = 'Beijing'
✅ WHERE name = 'Alice' AND city = 'Beijing'  -- 只用到 name 的索引
```

**用不到索引的查询**：

```sql
❌ WHERE age = 25
❌ WHERE city = 'Beijing'
❌ WHERE age = 25 AND city = 'Beijing'
```

### 为什么？

索引是按 `(name, age, city)` 顺序排列的，就像电话簿按"姓 → 名"排序：

- 找"姓张的人"：✅ 快速定位
- 找"名叫三的人"：❌ 必须从头翻

### 面试题

```sql
CREATE INDEX idx_abc ON t(a, b, c);

-- 下面哪个能用到索引？
1. WHERE a = 1 AND b = 2 AND c = 3  -- ✅ 全用上
2. WHERE a = 1 AND c = 3            -- ⚠️ 只用到 a
3. WHERE b = 2 AND c = 3            -- ❌ 跳过了 a
4. WHERE a = 1 AND b > 2 AND c = 3  -- ⚠️ 只用到 a, b（范围后失效）
```

## 使用 EXPLAIN 分析查询

## 使用 EXPLAIN 分析查询

`EXPLAIN` 是你的"X光镜"，能看穿 SQL 的执行计划。

```sql
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com';
```

**输出示例**：

```
+----+-------------+-------+------+---------------+-----------+---------+-------+------+-------+
| id | select_type | table | type | possible_keys | key       | key_len | ref   | rows | Extra |
+----+-------------+-------+------+---------------+-----------+---------+-------+------+-------+
|  1 | SIMPLE      | users | ref  | idx_email     | idx_email | 402     | const |    1 | NULL  |
+----+-------------+-------+------+---------------+-----------+---------+-------+------+-------+
```

### 重点关注的字段

| 字段 | 好的值 | 坏的值 | 说明 |
|------|--------|--------|------|
| **type** | `const`, `eq_ref`, `ref` | `ALL` | 访问类型，ALL 是全表扫描 ❌ |
| **key** | 你创建的索引名 | `NULL` | 实际使用的索引，NULL 表示没用索引 ❌ |
| **rows** | 越少越好 | 几千、几万 | 扫描的行数 |
| **Extra** | `Using index` | `Using filesort`, `Using temporary` | Using index 是覆盖索引 ✅ |

### type 字段详解

从快到慢：

```
const > eq_ref > ref > range > index > ALL
```

- **const**：通过主键或唯一索引查询单条记录（最快）
  ```sql
  SELECT * FROM users WHERE id = 1;
  ```

- **ref**：通过非唯一索引查询
  ```sql
  SELECT * FROM users WHERE email = 'alice@example.com';
  ```

- **range**：索引范围扫描
  ```sql
  SELECT * FROM users WHERE age > 18;
  ```

- **ALL**：全表扫描（最慢，要优化）
  ```sql
  SELECT * FROM users WHERE YEAR(created_at) = 2024;  -- 函数破坏索引
  ```

## 实战：优化慢查询

### 案例 1：没有索引

```sql
-- 慢查询（扫描 100万行）
SELECT * FROM users WHERE email = 'alice@example.com';
```

**EXPLAIN 结果**：
- type: `ALL`
- key: `NULL`
- rows: `1000000`

**解决方案**：

```sql
CREATE INDEX idx_email ON users(email);
```

**优化后**：
- type: `ref`
- key: `idx_email`
- rows: `1`

### 案例 2：索引失效

```sql
-- ❌ 函数破坏索引
SELECT * FROM users WHERE YEAR(created_at) = 2024;

-- ✅ 改写为范围查询
SELECT * FROM users 
WHERE created_at >= '2024-01-01' 
  AND created_at < '2025-01-01';
```

### 案例 3：隐式类型转换

```sql
-- ❌ 字段是 VARCHAR，但查询用了数字
SELECT * FROM users WHERE phone = 13800138000;  -- 索引失效！

-- ✅ 加引号
SELECT * FROM users WHERE phone = '13800138000';
```

### 案例 4：LIKE 通配符

```sql
-- ❌ 前置 % 无法使用索引
SELECT * FROM users WHERE username LIKE '%alice%';

-- ✅ 后置 % 可以使用索引
SELECT * FROM users WHERE username LIKE 'alice%';
```

## 什么时候不需要索引？

并非所有字段都要加索引：

1. **小表**（<1000 行）：全表扫描比走索引还快
2. **高频更新的字段**：索引会拖慢 INSERT/UPDATE
3. **选择性低的字段**：如性别（只有男/女）
4. **很少查询的字段**

### 索引的代价

```sql
INSERT INTO users (username, email, age) VALUES ('alice', 'alice@ex.com', 25);
```

如果 `username`, `email`, `age` 都有索引：
- ✅ 查询快了
- ❌ 插入慢了（需要更新 4 个索引：主键 + 3个字段）
- ❌ 占用更多磁盘空间

**权衡**：只在高频查询的字段上加索引。

## 索引设计原则

### 1. 区分度高的字段优先

```sql
-- ✅ email（每个用户不同）
CREATE INDEX idx_email ON users(email);

-- ❌ gender（只有男/女）
CREATE INDEX idx_gender ON users(gender);  -- 意义不大
```

### 2. 联合索引顺序

```sql
-- ✅ 区分度高的在前
CREATE INDEX idx_city_age ON users(city, age);

-- 如果常查："北京 + 18岁" 的用户
-- city 区分度高（几百个城市），放前面
```

### 3. 覆盖索引减少回表

```sql
-- 创建联合索引
CREATE INDEX idx_name_age_city ON users(name, age, city);

-- 这个查询不需要回表（覆盖索引）
SELECT name, age, city FROM users WHERE name = 'Alice';

-- 这个需要回表（查询了 email）
SELECT name, age, city, email FROM users WHERE name = 'Alice';
```

## 练习题

### 练习 1：创建合适的索引

有一个订单表：

```sql
CREATE TABLE orders (
  id INT PRIMARY KEY,
  user_id INT,
  order_no VARCHAR(50),
  status ENUM('pending', 'paid', 'shipped', 'completed'),
  created_at TIMESTAMP
);
```

**查询场景**：
1. 查询某个用户的所有订单：`WHERE user_id = ?`
2. 按订单号查询：`WHERE order_no = ?`
3. 查询某个用户的待支付订单：`WHERE user_id = ? AND status = 'pending'`

<details>
<summary>应该创建哪些索引？</summary>

```sql
-- 1. user_id 查询频繁
CREATE INDEX idx_user_id ON orders(user_id);

-- 2. order_no 唯一，且经常查询
CREATE UNIQUE INDEX idx_order_no ON orders(order_no);

-- 3. 联合索引（覆盖场景 1 和 3）
CREATE INDEX idx_user_status ON orders(user_id, status);
```

**为什么不创建单独的 status 索引？**
因为 status 区分度低（只有 4 个值），单独索引意义不大。

</details>

### 练习 2：分析查询

```sql
EXPLAIN SELECT * FROM users 
WHERE age > 18 AND city = 'Beijing';
```

如果只有索引 `idx_age_city(age, city)`，这个查询效率如何？

<details>
<summary>查看答案</summary>

**会使用索引**，但效率不是最优：
- `age > 18` 是范围查询
- 范围查询后，`city` 部分的索引失效

**优化方案**：
- 如果经常按 `city` 精确匹配，改为 `idx_city_age(city, age)`
- 或者创建两个单独索引，让优化器选择

```sql
CREATE INDEX idx_city_age ON users(city, age);
```

</details>

## 总结

**索引的核心原则**：
- ✅ 在 WHERE、ORDER BY、JOIN 的字段上加索引
- ✅ 区分度高的字段优先
- ✅ 联合索引遵循最左前缀原则
- ✅ 使用 EXPLAIN 验证索引效果

**避免索引失效**：
- ❌ 不要在索引字段上使用函数
- ❌ 避免隐式类型转换
- ❌ LIKE 不要前置 %

**用 EXPLAIN 分析**：
- type 不要是 ALL
- key 不要是 NULL
- rows 越少越好

1. **避免 `SELECT *`**：只查需要的字段，增加覆盖索引的几率。
2. **避免在索引列上做计算**：
   - ❌ `WHERE YEAR(created_at) = 2023` (函数破坏索引)

3. **模糊查询注意**：
   - ❌ `LIKE '%test'` (前缀模糊，索引失效)
   - ✅ `LIKE 'test%'` (后缀模糊，索引有效)
4. **OR 要小心**：
   - 如果 `WHERE a=1 OR b=2`，除非 a 和 b 都有索引，否则可能全表扫描。
