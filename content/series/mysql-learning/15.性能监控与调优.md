# 性能监控与调优

当网站变慢时，PM 会问前端"是不是 React 渲染慢了？" 前端一看 Network 面板，"不是啊，API 等了 5 秒才返回，是后端慢。" 后端一看，"数据库 CPU 100% 了。"

本章教你当这一刻来临时，如何像侦探一样通过 MySQL 找到凶手。

## 1. 开启慢查询日志 (Slow Query Log)

这是最直接的手段。告诉 MySQL："凡是执行时间超过 N 秒的 SQL，都给我记下来。"

### 配置
```ini
[mysqld]
# 开启日志
slow_query_log = 1
# 记录的文件位置
slow_query_log_file = /var/log/mysql/mysql-slow.log
# 阈值：超过 1 秒就算慢（生产环境通常设 1 或 2 秒）
long_query_time = 1
# 没有使用索引的查询也记下来（可选，优化神器）
log_queries_not_using_indexes = 1
```

### 分析日志
直接看日志文件很累，用 `mysqldumpslow` 工具聚合分析。
```bash
# 找出访问次数最多的 10 条 SQL
mysqldumpslow -s c -t 10 /var/log/mysql/mysql-slow.log
```

## 2. 也是 EXPLAIN

抓到了慢 SQL 之后怎么办？参考[第 8 章](./8.索引与查询优化.md)，用 `EXPLAIN` 看看它为什么慢（通常是因为没走索引）。

## 3. SHOW PROCESSLIST

"网站现在卡死了，谁在搞鬼？"
运行这个命令查看当前正在运行的所有连接。

```sql
SHOW PROCESSLIST;
-- 或者用更完整的
SELECT * FROM information_schema.processlist ORDER BY time DESC;
```

如果你看到某个 SQL 状态是 `Sending data` 并且 `Time` 很大，或者 `State` 是 `Waiting for table metadata lock`，那就是它了。你可以用 `KILL [ID]` 杀掉它应急。

## 4. Performance Schema

MySQL 8.0 默认开启的一套极其详细的监控系统。它记录了每一类操作（如 I/O, 锁, 内存）消耗了多少时间。

```sql
-- 查看哪些 SQL 语句消耗时间最长
SELECT * FROM sys.statement_analysis 
ORDER BY avg_latency DESC 
LIMIT 5;

-- 查看哪个表被扫描得最多（可能缺索引）
SELECT * FROM sys.io_global_by_file_by_bytes 
LIMIT 5;
```

## 5. 常见参数调优 (Configuration Tuning)

不要去背几百个参数，抓住这几个核心的（针对 InnoDB）：

1. **`innodb_buffer_pool_size` (最重要)**
   - 作用：把磁盘数据缓存在内存里。
   - 建议：如果是专用的 MySQL 服务器，设为物理内存的 **70%-80%**。如果太小，数据库频繁读盘，必慢。

2. **`innodb_log_file_size`**
   - 作用：Redo log 的大小。
   - 建议：大一点（如 1G 或 4G），能减少 checkpoint 频率，提升写入性能。

3. **`max_connections`**
   - 作用：最大并发连接数。
   - 建议：根据应用负载设，太小会 `Too many connections` 报错，太大会耗尽内存。通常 500-1000。

**注意**：参数调优是玄学更是科学，修改前务必基准测试。**大部分情况下，默认配置 + 合理的索引 就能解决 99% 的问题**。不要迷信"改个参数性能翻倍"的神话。
