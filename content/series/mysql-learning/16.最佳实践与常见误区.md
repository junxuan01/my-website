# 最佳实践与常见误区

这章是"老司机的经验之谈"。无论你前面的理论掌握得如何，遵守这些规则能让你少加很多班。

## 1. Schema 设计规范

### ✅ DO
1. **必须有主键**：InnoDB 必须有主键（最好是自增 ID 或 Snowflake ID），不要用 UUID 做主键（太长、无序，导致页分裂）。
2. **Not NULL**：尽量把字段设为 `NOT NULL`，空值给个 default（如空字符串）。因为 MySQL 中 `NULL` 值的索引处理比较特殊且麻烦。
3. **类型合适**：存状态用 `TINYINT` 别用 `INT`，存 IP 用 `INT UNSIGNED`（有函数互转）别用 `VARCHAR`。
4. **注释**：每个字段都加上 `COMMENT`，为了你自己，也为了接手你代码的人。

### ❌ DON'T
1. **不要用外键约束 (Foreign Key)**：
   - *震惊*：书上不是说要用吗？
   - *现实*：在互联网高并发场景，外键会带来额外的锁开销，且导致分库分表困难。**数据一致性通常由 App 层（Node.js 代码）来保证**。
2. **不要存大文件**：图片、视频别直接存数据库 `BLOB` 字段，存 URL 路径，文件放 S3/OSS。

## 2. SQL 编写规范

### ✅ DO
1. **WHERE 顺序**：把过滤数据最多的条件放在前面（虽然优化器会优化，但这是好习惯）。
2. **EXPLAIN**：上线前每条复杂 SQL 都要跑一遍 EXPLAIN。

### ❌ DON'T
1. **禁止 `SELECT *`**：如果你表里有个 `TEXT` 大字段，全查出来会把网卡打爆。
2. **禁止循环查询**（N+1 问题）：
   - 错误：先查出 100 个 User，然后循环 100 次去查每个人的 Orders。
   - 正确：`SELECT * FROM orders WHERE user_id IN (1, 2, ... 100)`。
3. **禁止隐式转换**：
   - 如果 `phone` 是字符串，查询别写 `WHERE phone = 123456`，要写 `WHERE phone = '123456'`。否则索引失效。

## 3. 三范式 vs 反范式

- **三范式 (3NF)**：数据不冗余。
  - 比如：订单表只存 `user_id`，不存 `username`。要显示用户名必须 JOIN。
- **反范式 (Denormalization)**：适当冗余以换取性能。
  - 比如：在订单表里多存一份 `username` 和 `user_phone`。这样查订单详情就不用 JOIN 用户表了。历史订单里的快照信息也不会因为用户改名而改变。

**建议**：互联网业务通常在 **第二范式** 基础上做适度冗余（反范式）。

## 4. 事务陷阱

1. **大事务**：别在事务里做 HTTP 请求！
   - 错误：`开启事务 -> 扣余额 -> 调用微信支付 API (等待 6 秒) -> 提交`。
   - 后果：这 6 秒你一直锁着数据库，别人都堵死了。
   - 正确：先把 API 调完，拿到结果，再快速开启事务写库。

2. **滥用事务**：简单的单条 UPDATE 不需要显式开启事务（MySQL 默认 AutoCommit）。
