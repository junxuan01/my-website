# 事务与并发控制

Web 世界大部分时候是并发的。当两个用户同时抢购最后一个商品，或者你同时在两个手机通过转账操作同一个账户，数据库如何保证数据不乱套？这就需要 **事务 (Transaction)** 和 **并发控制**。

## 1. 什么是事务？

事务是一组 SQL 操作的集合，它们是一个不可分割的工作单位。

```sql
START TRANSACTION;

-- 1. 扣 A 的钱
UPDATE accounts SET balance = balance - 100 WHERE user_id = 'A';

-- (如果这里断电了，或者报错了)

-- 2. 加 B 的钱
UPDATE accounts SET balance = balance + 100 WHERE user_id = 'B';

COMMIT; -- 提交事务：只有两步都成功，才一起生效
-- ROLLBACK; -- 回滚事务：只要有一步失败，全部撤销，就像没发生过一样
```

## 2. ACID 特性 (背诵全文)

面试必背，理解优先。

- **Atomic (原子性)**：要么全做，要么全不做。实现靠 **undo log**。
- **Consistency (一致性)**：数据处于合法状态。
- **Isolation (隔离性)**：并发事务互不干扰。实现靠 **MVCC (多版本并发控制)** 和 **锁**。
- **Durability (持久性)**：提交就永久保存。实现靠 **redo log**。

## 3. 并发带来的问题

如果没有隔离性，并发会带来这三个问题：

1. **脏读 (Dirty Read)**：
   - A 正在改数据但还没提交，B 读到了 A 改的数据。然后 A 回滚了，B 读到的是假数据。
2. **不可重复读 (Non-repeatable Read)**：
   - B 在一个事务里查了两次余额，第一次是 100。中间 A 修改并提交了。B 第二次查变成了 0。B 懵了：我没动啊，怎么变了？
3. **幻读 (Phantom Read)**：
   - B 查所有 "分数为 100" 的学生，发现有 3 个。中间 A 插入了一个新学生也是 100 分。B 准备给这 3 个学生发奖状（UPDATE），结果发现更新了 4 行记录！就像出了幻觉。

## 4. 四种隔离级别

MySQL 提供了四种级别来解决上述问题（级别越高，越安全，性能越低）。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|----------|------|------------|------|------|
| **READ UNCOMMITTED** (读未提交) | 发生 | 发生 | 发生 | 裸奔，没人用 |
| **READ COMMITTED** (读已提交) | ❌ | 发生 | 发生 | Oracle/PG 的默认级别 |
| **REPEATABLE READ** (可重复读) | ❌ | ❌ | ❌ (大部分解决) | **MySQL 的默认级别！** |
| **SERIALIZABLE** (串行化) | ❌ | ❌ | ❌ | 此时完全不并发，排队执行。最安全但最慢 |

**为什么 MySQL 默认是 Repeatable Read (RR)?**
因为在 RR 级别下，MySQL 使用 **Next-Key Lock** 算法解决了大部分幻读问题，同时性能损失不大，是一个很好的平衡点。

## 5. 锁机制 (Locking)

当事务冲突时，MySQL 用锁来协调。

### 按粒度分
1. **行锁 (Row Lock)**：InnoDB 特有。只锁住你操作的那一行。并发高。
2. **表锁 (Table Lock)**：锁住整张表。其他人只能看不能改。并发低。

### 按类型分
1. **共享锁 (S Lock) / 读锁**：
   - `SELECT ... LOCK IN SHARE MODE`
   - 我读的时候，允许你也读，但你不许改。
2. **排他锁 (X Lock) / 写锁**：
   - `SELECT ... FOR UPDATE` 或 `UPDATE/DELETE` 自动加。
   - 我在改，你们谁也别想读，谁也别想改。

## 6. 死锁 (Deadlock)

**场景**：
- 事务 A 锁住了资源 1，想要资源 2。
- 事务 B 锁住了资源 2，想要资源 1。
- 两人互不相让，这就叫死锁。

**解决**：
- MySQL 会自动检测死锁，并强行回滚其中一个事务（通常是改动较少的那个），让另一个通过。
- **开发建议**：保持多表操作的顺序一致。比如所有代码都先锁 Users 表，再锁 Orders 表。

## 7. 实战：乐观锁 vs 悲观锁

除了数据库层面的锁，我们在业务代码（Node.js）中也常手动实现锁。

**悲观锁 (Pessimistic Locking)**：
- 直接依赖数据库 `FOR UPDATE`。
- 适合写竞争非常激烈的场景。
```sql
START TRANSACTION;
SELECT stock FROM goods WHERE id = 1 FOR UPDATE; -- 锁住！
-- 检查库存
UPDATE goods SET stock = stock - 1 WHERE id = 1;
COMMIT;
```

**乐观锁 (Optimistic Locking)**：
- 更加"前端"的做法。不真锁，而是通过版本号 `version` 控制。
- 适合读多写少的场景（比如抢票虽然人多，但其实大部分在刷页面）。
```sql
-- 1. 先查出来版本号
SELECT stock, version FROM goods WHERE id = 1; -- 假设 version = 5

-- 2. 更新时带上版本号
UPDATE goods 
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 5; -- 关键在这里

-- 3. 检查 affectedRows。如果是 0，说明被别人插队改了 version，前端提示"重试"。
```
